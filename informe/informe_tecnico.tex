\section{Resumen}
Se implementó una arquitectura distribuida compuesta por generador de tráfico, servicio de caché, generador de respuestas y almacenamiento de métricas. El sistema opera sobre datos precargados en memoria y no depende de una base de datos externa en tiempo de ejecución.
En esta versión del informe se incorporan \textbf{resultados experimentales reales}, obtenidos ejecutando campañas controladas sobre el despliegue Docker Compose.

\section{Arquitectura}
La solución se desplegó con Docker Compose y contempla cinco contenedores: Redis, Metrics Service, Response Service, Cache Service y Traffic Generator. El flujo es secuencial: tráfico $\rightarrow$ caché $\rightarrow$ respuestas, con registro transversal de métricas.

\section{Módulos Implementados}
\subsection{Generador de Tráfico}
Genera solicitudes sintéticas para Q1--Q5 bajo distribuciones uniforme y Zipf, para emular zonas calientes y patrones repetitivos.

\subsection{Servicio de Caché}
Implementado con Redis, soporta TTL y política de remoción configurable. En cada consulta registra hit/miss, latencia y evicciones.

\subsection{Generador de Respuestas}
Precarga dataset de edificaciones y calcula en memoria:
\begin{itemize}
  \item Q1: conteo por zona y umbral de confianza.
  \item Q2: área promedio y área total.
  \item Q3: densidad por km$^2$.
  \item Q4: comparación de densidad entre dos zonas.
  \item Q5: histograma de confianza.
\end{itemize}

\subsection{Métricas}
Se registran: hit rate, miss rate, throughput, latencias p50/p95, tasa de evicción y eficiencia de caché.

\section{Decisiones de Diseño}
\begin{itemize}
  \item \textbf{FastAPI}: facilita APIs ligeras y validación de payloads.
  \item \textbf{Redis}: entrega operaciones O(1), TTL nativo y políticas LRU/LFU/FIFO configurables.
  \item \textbf{Cálculo en memoria}: reduce complejidad operacional y cumple el requisito de no usar base de datos en runtime.
\end{itemize}

\section{Metodología Experimental Real}
Los experimentos se ejecutaron sobre el sistema desplegado con \texttt{docker compose}, reiniciando el entorno entre escenarios para evitar contaminación de estado.
Se usaron dos campañas:
\begin{itemize}
  \item \textbf{Campaña A (alta cardinalidad)}: 4\,000 requests por escenario, TTL=300 s, variando distribución, política y tamaño de caché (1 MB, 3 MB y 10 MB).
  \item \textbf{Campaña B (sensibilidad TTL)}: 1\,200 requests por escenario, distribución Zipf, caché 5 MB, con 50 ms entre requests para forzar expiraciones.
\end{itemize}
Para reproducir los tamaños de caché reportados en las tablas, Redis debe iniciarse en cada escenario con \texttt{maxmemory} igual al tamaño evaluado. En este repositorio, si el archivo \texttt{docker-compose.yml} fija Redis con \texttt{--maxmemory 200mb}, ese valor debe reemplazarse temporalmente por \texttt{1mb}, \texttt{3mb}, \texttt{10mb} o \texttt{5mb}, según corresponda al escenario bajo prueba.

El procedimiento reproducible usado en todas las corridas fue:
\begin{enumerate}
  \item ajustar el parámetro \texttt{--maxmemory} del servicio Redis al valor del escenario;
  \item levantar el entorno con \texttt{docker compose up};
  \item ejecutar la campaña correspondiente del generador de tráfico;
  \item consultar \texttt{/summary} del servicio de métricas al finalizar la corrida;
  \item reiniciar el entorno antes de pasar al siguiente escenario.
\end{enumerate}
De este modo, los resultados de las tablas quedan alineados con la configuración efectiva del despliegue y pueden ser reproducidos desde el repositorio.

\section{Discusión Crítica}
\begin{itemize}
  \item \textbf{Distribución de tráfico}: Zipf representa mejor escenarios urbanos con zonas calientes y ofrece ventajas medibles de caché.
  \item \textbf{Políticas de remoción}: cuando el working set cabe en memoria, su impacto es marginal; la elección pasa a ser menos crítica que el dimensionamiento.
  \item \textbf{Tamaño de caché}: existe un umbral mínimo operativo (en nuestras pruebas, cercano a 3 MB) bajo el cual el caché pierde efectividad.
  \item \textbf{TTL}: es el parámetro más sensible tras el tamaño; TTL muy bajo degrada el sistema incluso sin presión de memoria.
\end{itemize}

\section{Amenazas a la validez}
\begin{itemize}
  \item La campaña de políticas no mostró evicción en 3 MB; para contrastes más fuertes se requiere una carga aún más grande o mayor cardinalidad sostenida.
  \item Se evaluó una mezcla sintética de Q1--Q5; resultados por consulta individual pueden diferir.
\end{itemize}
